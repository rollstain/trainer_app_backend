# Порядок работы в репозитории

Правила для любого, кто вносит правки, — человека или ассистента. Устройство сервиса и запуск —
в `README.md`.

## Ветка на задачу

Прямых коммитов в `main` нет. Любая задача начинается с ветки от свежего `main`:

```bash
git fetch origin
git checkout -b feature/coach-working-hours origin/main
```

Имя ветки — `<тип>/<суть>`: латиница, kebab-case, два-четыре слова о сути, а не о файлах.

| Тип | Когда |
|---|---|
| `feature/` | новая функциональность |
| `fix/` | исправление дефекта |
| `refactor/` | правка без изменения поведения |
| `chore/` | сборка, CI, зависимости, инфраструктура |
| `docs/` | только документация |

## Коммит

Одна строка по-русски, описывающая сделанное: «Подтверждение почты: токены с письмом, вытеснение
неподтверждённых адресов». Без служебных трейлеров и ссылок на сессии. Тело — только если одной
строки не хватает на «почему».

Сообщения коммитов попадают в описание релиза, поэтому пишутся для человека.

## Завершение работы

```bash
git push -u origin <ветка>
gh pr create --fill --base main
```

Описание — по шаблону `.github/pull_request_template.md`. Сливает владелец репозитория,
автор PR не мержит сам. CI на PR обязан быть зелёным.

## Релиз и выкатка

Релиз — тег на `main`:

```bash
git tag -a v0.3.0 -m "Рабочие часы тренера, подтверждение почты"
git push origin v0.3.0
```

`release.yml` соберёт jar и создаст GitHub Release со списком изменений от прошлого тега.
**Выкатка на прод при этом не происходит** — она отдельным действием: Actions → **Deploy** →
**Run workflow**, выбрать тег. Пайплайн снимет дамп базы, заменит jar, перезапустит сервис,
проверит живость и вернёт прежний jar, если проверка не прошла.

Порядок и секреты — `docs/deploy.md`.

## Правила кода

- Слои: `Controller` → `Service` → `Repository` → `Entity`. Контроллер не ходит в репозиторий,
  сервис не отдаёт наружу entity.
- Комментариев в коде нет. Нужен комментарий — плохо названа функция или переменная.
- `!!` запрещён: `checkNotNull` с сообщением или ветвление.
- Числовые литералы — в `private const val` с именем, объясняющим значение целиком.
- Схему ведёт только Flyway. `ddl-auto` остаётся `validate`.
- Номер миграции не переиспользуется и не вставляется в середину; имя таблицы или индекса
  не занимается повторно — это проверяет `scripts/check_migrations.py`.
- Миграция совместима с предыдущей версией кода: сначала добавляем, потом переключаем чтение,
  удаляем следующим релизом. Откат jar миграцию не отменяет.
- Секреты только через переменные окружения. Значения по умолчанию для них в `application.yml`
  пустые, а не рабочие.
