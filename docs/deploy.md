# Выкатка на прод

## Порядок

1. Задача слита в `main`, CI зелёный.
2. Тег на `main` — `release.yml` собирает jar и создаёт GitHub Release со списком изменений.
   Прод при этом не трогается.
3. Actions → **Deploy** → **Run workflow**, в поле `ref` — тот же тег. Пайплайн:
   - проверяет миграции и гоняет тесты;
   - собирает `bootJar`;
   - по SSH передаёт jar на сервер, где `ci_deploy.sh` снимает дамп базы, подменяет jar,
     перезапускает сервис и три минуты ждёт `UP` от `/actuator/health`;
   - если живость не подтвердилась — возвращает прежний jar, перезапускает сервис и роняет прогон
     с последними строками журнала;
   - в Telegram уходит короткое сообщение об исходе.

Разделение «релиз» и «выкатка» намеренное: тег фиксирует, что поехало, кнопка отвечает за то,
когда это увидит прод.

## Что откат не чинит

Возврат jar не отменяет применённые миграции. Схема откатывается только из дампа, который
`ci_deploy.sh` снимает **до** подмены jar. Поэтому каждая миграция обязана быть совместимой
с предыдущей версией кода: сначала добавляем колонку и пишем в неё, следующим релизом переключаем
чтение, удаляем через релиз.

Если дамп не появился в `/opt/trainer/backups`, выкатка не начинается: молча выкатываться
без точки возврата нельзя.

## Секреты репозитория

| Секрет | Что это |
|---|---|
| `DEPLOY_HOST` | адрес прод-сервера |
| `DEPLOY_USER` | пользователь SSH |
| `DEPLOY_SSH_KEY` | приватный ключ отдельной пары, заведённой только для CI |
| `DEPLOY_KNOWN_HOSTS` | строка из `ssh-keyscan` для этого сервера |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | уведомления; без них шаг пропускается |

Ключ входа с рабочей машины в секреты не кладётся: у CI своя пара, её можно отозвать одной
строкой, не трогая остальные доступы.

## Разовая настройка сервера

Ключ для CI генерируется локально и **не** имеет пароля — иначе пайплайн им не воспользуется:

```bash
ssh-keygen -t ed25519 -f trainer-ci -N "" -C "github-actions"
```

На сервере публичная часть кладётся с принудительной командой: по этому ключу нельзя получить
шелл, можно только запустить выкатку.

```bash
install -m 755 scripts/ci_deploy.sh /opt/trainer/ci_deploy.sh
printf 'command="/opt/trainer/ci_deploy.sh",restrict %s\n' "$(cat trainer-ci.pub)" \
  >> ~/.ssh/authorized_keys
```

Приватная часть и отпечаток сервера уезжают в секреты:

```bash
gh secret set DEPLOY_SSH_KEY < trainer-ci
gh secret set DEPLOY_KNOWN_HOSTS --body "$(ssh-keyscan -t ed25519 <адрес сервера>)"
gh secret set DEPLOY_HOST
gh secret set DEPLOY_USER
```

Локальный файл `trainer-ci` после этого удаляется, `trainer-ci.pub` не нужен.

## Проверка вручную

```bash
curl -s https://api.lyashukfit.ru/actuator/health
```

Ответ `{"status":"UP"}` означает, что поднялись и приложение, и подключение к базе. Подробностей
ручка не отдаёт намеренно: снаружи видно только «жив или нет».

## Если пайплайн недоступен

Тот же порядок руками: снять дамп, скопировать jar в `/tmp`, сохранить текущий в `.bak`, подменить,
`systemctl restart trainer`, посмотреть журнал и проверить `flyway_schema_history`. Это запасной
путь, а не основной: руками легко пропустить дамп.
